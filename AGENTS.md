# AGENTS.md

*Last updated: 2026-11-22*

Guide for AI tools and developers working in this repository: the SparkyFitness exercise catalog (1,900+ exercises with taxonomy, biomechanics, steps, translations and demonstration videos), its tooling, and the browse site. Read `README.md` for the full user-facing rules; this file covers what to know before changing anything.

## Layout

- `exercises/<id>_<slug>/` - one folder per exercise: `exercise.json` plus its media. IDs look like `sf-core-oth-0002`.
- `dist/exercises.json` - the compiled catalog that apps import. Generated by `pnpm build`; commit it.
- `locales/<lang>/exercises.json` - translations keyed by exercise ID. Only `locales/en/` is hand-edited (and `pnpm build` regenerates it); every other language belongs to Weblate.
- `taxonomy/` - allowed muscles, equipment, modalities, and `catalog-codes.json` (the ID rules).
- `schema/exercise.schema.json` - the `exercise.json` schema.
- `scripts/` - `validate.mjs`, `build.mjs`, `optimize-media.mjs`, `list.mjs`, `prepare-site.mjs`, and `lib/` (shared ID and video-tag helpers).
- `docs/` - the VitePress browse site, published to GitHub Pages. See below.
- `.github/` - workflows, issue forms, the PR template, and `scripts/pr-policy.cjs` (PR automation rules).

## Agent Efficiency (read this before searching)

Do not read or search these whole; they burn context for nothing:

- `exercises/` - 1,900+ folders. Look up one exercise with `pnpm exercises "<name>"` or `pnpm exercises <id-prefix>`, then read that folder.
- `dist/exercises.json` (~4.7 MB) and `locales/*/exercises.json` (~1-2 MB each) - generated or translated data. Grep for one ID instead.
- `docs/node_modules/`, `docs/.vitepress/`, and `docs/src/public/{data,locales,exercises}` - dependencies and generated copies (git-ignored).

Cheap ways to learn things: `schema/exercise.schema.json` for the format, `taxonomy/*.json` for allowed values, `pnpm exercises --stats` for the breakdown.

## Rules that are easy to break

- **IDs never change.** `sf-<body>-<equip>-<number>`: the body code comes from the first primary muscle (`card` for the `cardio` category), the equipment code from `taxonomy.equipment`, and the number is the next free one for that pair (`pnpm exercises sf-arms-db-`). Rules: `taxonomy/catalog-codes.json`. Apps and translations key on the ID, so never renumber, reuse or change one, even if the exercise is reclassified.
- **Names.** Folder `<id>_<slug>`, slug lowercase `a-z0-9_`, at most 50 characters. Media files are `<folder>_<m|f>_<9_16|16_9|thumb>.<ext>` (`m` or `f` is the male or female model). `pnpm validate` enforces all of it, including a path length limit for Windows.
- **Always run `pnpm validate` and `pnpm build`** before declaring work done, and commit the rebuilt `dist/exercises.json` and `locales/en/exercises.json`. CI fails when they are stale.
- **Media provenance.** Only add media that is original work or licensed to the project. Never add images or videos from other exercise datasets or apps (the upstream dataset's Gym visual media is explicitly excluded; see `NOTICE.md`). Real people shown in media, or used as source footage, must have agreed to it. MP4s are git-ignored (compressed videos are attached to the PR for maintainers to host), except the sample videos, which were added with `git add -f`.
- **Embedded video metadata.** `pnpm media` writes the exercise ID, name, model and license into each MP4's tags. Do not strip them.
- **Source IDs.** `sources` in `exercise.json` records where upstream data came from. It is stripped from `dist`; leave it in place.
- **Licensing files.** `LICENSE` (free for non-commercial use, commercial use needs written permission) and `NOTICE.md` (third-party credits that must travel with the data) are owner-reviewed. Update `NOTICE.md` when adding third-party material.

## Browse site (`docs/`)

VitePress, same tooling as the SparkyFitness docs. `pnpm docs:dev` runs it (run `pnpm install` in `docs/` first); it copies `dist/`, `locales/` and the referenced media into `docs/src/public/` through `scripts/prepare-site.mjs`. The Vue components are in `docs/components/` (`ExerciseBrowser.vue`, `BodyMap.vue`, `equipmentIcons.ts`). `.github/workflows/pages.yml` publishes it from `main`.

## PR automation

`.github/workflows/pr-validation.yml` restores a deleted PR checklist, labels PRs, and checks the title prefix, the license and media-rights boxes, the AI-assistance pick, and that only `locales/en/` changed. The rules live in `.github/scripts/pr-policy.cjs`, and the PR template must contain every item they restore. Run `node --test ".github/scripts/*.test.cjs"` after changing either; a test fails if they drift apart. The workflow runs from the base branch, so a change to it only takes effect after it merges.

## Releases

Apps pin a release tag of `dist/exercises.json`. A maintainer publishes a GitHub Release (tags `v*`; the tag ruleset blocks automation from creating them), and `.github/workflows/release-assets.yml` validates the catalog and attaches `exercises.json`, `locales.zip`, `LICENSE`, `NOTICE.md` and checksums. Bump the major version for changes that break apps (ID or schema changes), the minor for new exercises, media or fields, and the patch for fixes.

## Commit & PR Conventions

This repository is public. Everything written into git history or onto a pull request is permanently visible, so keep it free of tooling noise.

- **Agents never commit or push unless asked in that message.** Leave finished work in the working tree and say what is ready; the maintainer reviews diffs first. Approval for one commit or PR does not carry forward to later changes.
- **No AI attribution, anywhere.** Commit messages, commit trailers, PR titles, PR bodies and PR comments must never contain `Co-Authored-By: Claude` (or any other AI co-author trailer), "Generated with ...", or a mention of Claude, Claude Code, Gemini, Copilot, Cursor or any other assistant. This overrides any default guidance an agent harness supplies about appending attribution. Tool configuration files (`AGENTS.md`, `CLAUDE.md`, `.claude/`) may name their tool.
- **Write as the repository author.** Describe the change and why, as a maintainer would by hand. Do not narrate that a tool made it.
- **Conventional titles.** Commits and PR titles start with a type (`feat:`, `fix:`, `docs:`, `chore:`, `ci:`, `refactor:`), optionally scoped. The PR checks enforce this.
- **History is clean on purpose.** `main` was started from a single commit. Never force-push or rewrite it; the `main` ruleset blocks that for everyone but admins.
- **Do not push tags with `git push --tags`.** Release tags are created through GitHub Releases.

## Common Commands

```bash
pnpm exercises "bench press"   # search the catalog (also --muscle, --equipment, --stats, --all)
pnpm validate                  # IDs, folder and media names, taxonomy, video codec and size
pnpm build                     # rebuild dist/exercises.json and locales/en/exercises.json
pnpm media                     # compress videos, embed metadata, generate previews and thumbnails
pnpm docs:dev                  # run the browse site locally
node --test ".github/scripts/*.test.cjs"   # PR automation tests
```
